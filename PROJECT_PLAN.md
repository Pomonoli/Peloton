## Development stack and Linux readiness

- **Server and contracts.** Go with REST and Connect RPC backed by Protobuf. The module requires Go `1.26.10` and selects `go1.27.4`. Go stubs are checked in, while TypeScript stubs are generated by Buf with local `protoc-gen-go`, `protoc-gen-connect-go`, `protoc-gen-es` and `protoc-gen-openapiv2` binaries on `PATH`. See [go.mod](go.mod), [api/proto/buf.gen.yaml](api/proto/buf.gen.yaml), [Makefile](Makefile) and [docker/Dockerfile.build-base](docker/Dockerfile.build-base). [Go release downloads](https://go.dev/dl/)
- **Web.** SvelteKit and Svelte 5, TypeScript, Vite, Tailwind, MapLibre, uPlot and Paraglide. Use npm and the lockfile. `web/.nvmrc` pins Node `26.13.1` and the build-base Dockerfile pins `24.21.0`. The host’s `24.21.0` matches that Dockerfile and satisfies the Node engine ranges declared in the lockfile. Start with it for the local smoke test and reconcile the repo’s pins in later baseline work. See [web/package.json](web/package.json), [web/package-lock.json](web/package-lock.json) and [web/.nvmrc](web/.nvmrc).
- **Runtime.** Docker Engine and the Compose v2 plugin provide PostgreSQL 17 with TimescaleDB and PostGIS, NATS JetStream, Silo (the S3-compatible service named `minio`) and Mailpit. PostgreSQL holds activity and spatial data, S3 holds raw blobs, and NATS carries jobs and activity follow-ups. [docker-compose.dev.yml](docker-compose.dev.yml), [docs/architecture.md](docs/architecture.md)
- **Workflow and tests.** Bash, Git, GNU Make and a C compiler for `go test -race`. `make test` runs the DB-free Go race suite and Vitest. `make test-db-up` starts the disposable test DB and prints the `CAIRN_TEST_DATABASE_URL` for `make test-integration`. The DB role needs `CREATE DATABASE`. The full `make check` gate also needs the pinned tools from `make tools`, Buf plugins, gitleaks and a `v*` release tag for `proto-breaking`. No tags are available in this checkout. See [CONTRIBUTING.md](CONTRIBUTING.md) and [the Linux CI workflow](.github/workflows/check.yml).
- **Architecture.** [ADR 0002](docs/adr/0002-hexagonal-architecture.md) describes the layer boundaries. `cmd/server` wires Go use cases to PostgreSQL, S3 and NATS. File uploads and worker results converge on [the activity pipeline](internal/usecase/pipeline/), where processing is designed for retries. `docker/Dockerfile.core` embeds the production SPA and needs no separate web server at runtime.

Linux is a supported development and test environment. The baseline host is Linux Mint 22.3 on x86-64 with Node `24.21.0`, npm `11.19.0`, Make, Git and GCC. The baseline was missing Go, Docker/Compose, Buf, `protoc-gen-es`, installed web dependencies and generated TypeScript stubs.

Use the [Makefile](Makefile) and [tracked files](cmd/) when the README and [local guide](docs/run-local.md) disagree with the checkout. `make dev-worker` is absent, and both provider workers live outside this repo. `make dev-web` starts Vite without installing or generating anything. `make web-deps` installs the locked frontend dependencies and triggers protobuf generation on a fresh checkout. Plain `make build` produces a host API binary without `embedweb`, so use Vite or the core Docker build for the browser UI. The Makefile and build-base image also pin different versions of some protobuf tools.

## Implementation phases

### 1. Start the unchanged application locally

Provision Go `1.27.4` and Docker Engine with Compose v2. Obtain approval before privileged system changes. Use the existing Node `24.21.0` initially. Run from the repository root after provisioning, with the installed Go tools and the npm global bin directory on `PATH`.

```sh
go version
docker compose version
make proto-tools
npm install -g @bufbuild/protoc-gen-es@2.12.0
export PATH="$(go env GOPATH)/bin:$PATH"
make web-deps
( umask 077; test -e dev.env || cp dev.env.example dev.env )
docker compose -p peloton-dev -f docker-compose.dev.yml up -d --wait
```

In one terminal, start the server with the dev environment and bind it to loopback. The example environment enables auto-migration and supplies a development admin on first boot.

```sh
( set -a; . ./dev.env; set +a; CAIRN_HTTP_ADDR=127.0.0.1:8080 go run ./cmd/server serve )
```

In a second terminal run `make dev-web`. Verify `curl -fsS http://localhost:8080/readyz` and sign in at `http://localhost:5173/login` with the admin settings in `dev.env`. Keep the local settings and sample credentials confined to the dev machine. Run `make test`. For tagged integration tests, create a separate test database within the `peloton-dev` PostgreSQL service and set `CAIRN_TEST_DATABASE_URL` to that database. Upload the synthetic FIT and GPX rides to verify the API imports. **Done when** the browser can sign in, both uploads succeed, and the Linux test results are recorded.

**Local results on 21 November 2026.** On Linux Mint 22.3, Go `1.27.4` is installed in the ignored project tool directory. Run `source tmp/.dev-toolchain/env.sh` to activate it. Docker Engine `29.10.0` and Compose `2.40.3` run the four healthy `peloton-dev` services on loopback. All 76 migrations applied, and `/readyz` reports PostgreSQL, NATS and blob storage healthy. The browser rendered the sign-in form at `http://localhost:5173/login`. An invite created a local account, and a fresh session signed in by password. Synthetic FIT and GPX rides imported with 31 GPS samples each, returned their archived originals byte-for-byte and deduplicated on repeat upload. The test uncovered a cross-user upload identity bug. The lookup now scopes deduplication to the owner, and an HTTP integration test covers identical uploads by two accounts. After the fix, `make test` passed across 73 Go packages and 159 web tests. The tagged API and PostgreSQL integration suites also passed against a scratch database.

### 2. Validate manual import and friends-only behavior

Upload one known FIT, GPX and TCX ride through the browser. Validate elapsed time, distance, route and optional sensor streams. Re-upload the same files, confirm deduplication and check the stats, records, training load and personal heatmap. Use a second account to exercise invitations, following, kudos, comments and activity visibility. **Done when** both users can use the shared feed and their private rides and tracks stay private.

### 3. Prove segment discovery and local timing

Start a small, offline proof of concept with synthetic provider responses, one representative imported route and a deliberately nearby non-match. Build a bounded candidate lookup along the route, deduplicate by provider ID and test the returned geometry with the existing PostGIS and corridor matcher. Feed the result through existing local effort and ranking logic, with repeated traversal, parallel roads, opposite direction, sparse GPS, duplicate sources and permissions in the test data. Link discovery to the import follow-up so uploads can succeed if discovery is unavailable.

Evaluate publicly accessible segment information, undocumented endpoints and ordinary network traffic from accounts we control. Research these alternatives independently of official Strava API approval. Use a few known rides to compare segment coverage, geometry quality, request volume, throttling and cache behavior. Exclude private third-party data and stop any approach that requires compromised security controls. Record legal, security and account-ban risks separately from technical acceptance. **Done when** two local users produce the expected times and PRs, retrying yields the same result, and the prototype establishes which discovery methods are feasible and maintainable. Keep native or explicitly licensed segments available if the alternatives prove unreliable.

### 4. Prove Garmin automation and package the backend

Try an approved Garmin Activity API integration where feasible. Evaluate the existing worker separately for compatibility and authentication stability. Verify a historic or manually uploaded ride can coexist with a later automatic import, plus scheduled reconciliation, credential expiry, reauthorization and revocation. Keep file upload available throughout. Create a single-instance Compose bundle using the existing core image design, PostgreSQL, S3-compatible storage and NATS. Keep Garmin optional, Mailpit local-only, and federation disabled by default. Verify backups and a clean restore locally. **Done when** the Compose bundle boots and restores locally and Garmin either imports repeatably or has a documented fallback.

### 5. Ship the Android client and finish cycling features

Prototype the existing responsive SPA on a phone and package a thin Android client if it meets the authentication, upload and map requirements. Evaluate a native Kotlin client only if packaging fails those checks. Consolidate branding, use English as the sole shipped locale initially and move remaining labels, errors and notification text into the localization path. Prepare locale-aware units, dates and message plurals for `nl-BE`. Add simple cycling goals and a saved route library from existing ride tracks, then extend analytics where real activities reveal gaps. **Done when** a signed APK can connect to a configured HTTPS backend, sign in, upload a file and display the feed, maps and cycling stats.

## Architectural risks

### Strava access, coverage and data lifetime

- The official `GET /segments/explore` accepts rectangular bounds, returns at most ten results and is limited to Extended Access Tier apps granted permission. One bounding box may miss nearby candidates on a long or dense route. Use bounded windows and request limits for the proof of concept and measure missing candidates against known rides. [Strava API reference](https://developers.strava.com/docs/reference/#api-Segments-exploreSegments)
- The published Strava API terms cover competitive use, use with other customer data, derived analytics and persistent geographic indexes. They describe a seven-day cache limit and removal when a resource becomes unavailable. Document the legal, security and account-ban risks of each research approach, especially sharing geometry or ranks, and record endpoint instability and throttling separately. Design for provenance, expiry and deletion in the cache, related results, backups and logs. Keep discovery optional so its failures cannot block upload. [Strava API Agreement](https://www.strava.com/legal/api?hl=en) · [Strava API Policy, sections 5–6](https://www.strava.com/legal/api_policy)
- Cairn’s current provider segments are per linked account. Its matching work is per source, and new or edited segments do not automatically reprocess historical rides. Use scoped, batched backfill if needed. Define duplicate handling for multiple sources of one ride, and test that rankings honor visibility and count only local GPS traversals. [docs/segments-open-questions.md](docs/segments-open-questions.md) · [internal/usecase/segmentview/segments.go](internal/usecase/segmentview/segments.go)

### Garmin authentication and upkeep

- Garmin’s official program requires application approval and access that fits the use case. Published Starter access is push-only and excludes historical data. Confirm the implications for inbound connectivity and backfill before choosing it. [Garmin Connect Developer Program](https://developer.garmin.com/gc-developer-program/overview/)
- Cairn’s external Python worker uses `garminconnect` and unofficial Garmin Connect sign-in. MFA, session persistence, expiry, rate limiting and provider changes can interrupt unattended jobs. Check the pinned worker’s actual MFA and reconnect flow, credential storage and NATS scoping using a consenting test account. Keep reauthorization visible to users and avoid requesting credentials again on every retry. [Cairn Garmin worker](https://github.com/opencairn-org/cairn-provider-garmin) · [internal/adapter/primary/workerrpc/logins.go](internal/adapter/primary/workerrpc/logins.go)

### Android and private hosting

- Reusing the SPA minimizes duplicated UI work. Verify HTTPS certificate trust for the intended private hostname, backend URL setup, browser sign-in and redirect handling, Android file picker behavior, session expiry and MapLibre rendering on a real device. A same-origin shell can reuse the existing cookie flow. A native client should evaluate browser-based OAuth authorization code with PKCE and explicit write scopes against the existing API. Never embed a shared secret in the APK. [web/src/lib/connect.ts](web/src/lib/connect.ts) · [internal/usecase/oauthserver/server.go](internal/usecase/oauthserver/server.go) · [docs/api-scopes.md](docs/api-scopes.md)
- Keep GPS tracks and heatmaps owner-scoped by default. The current web basemap can contact external tile services, so verify what leaves the device when viewing private rides and configure a suitable tile source if needed. Verify only the app endpoint is exposed in the future Compose bundle and preserve license notices and applicable source obligations when distributing the service and APK.
